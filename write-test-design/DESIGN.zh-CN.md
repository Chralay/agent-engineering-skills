## 对话结论

“Queued 状态日志优化”对话最终确认的问题不是单纯的单测写法，而是测试产生得太晚：代码已经实现后再补单测，测试容易跟着方法、分支和 Mock 走，变成“证明代码执行过”，而不是“证明业务行为正确”。直接先写完整测试代码也不适合状态多、异步多、仍需探索的复杂前端功能。

推荐流程是：

```text
业务需求
↓
write-frontend-spec：定义做什么、行为契约和验收标准
↓
人工确认 Spec
↓
write-test-design：定义如何证明功能正确
↓
人工确认 Test Design
↓
编码实现
↓
write-unit-test：根据完整 Test Design 编写自动化测试
```

因此，`write-test-design` 补的是 `Spec → 测试覆盖` 的中间层。它不重新设计架构，也不直接生成 Vitest、Vue Test Utils 或其他测试代码。

## Skill 定位

`write-test-design` 根据已确认的前端功能技术 Spec，生成业务可读、可追踪、可交给实现和自动化测试继续使用的测试设计。

它主要回答三个问题：

1. 如何证明这个功能正确？
2. 哪些状态、异常、边界和竞态必须覆盖？
3. 每条业务规则适合自动化验证还是人工验证？

第一版聚焦前端功能测试设计。后续是否扩展到后端或系统级测试设计，单独评估，不在本版预留抽象。

## 输入与事实来源

### 必需输入

- 已经人工确认的 Frontend Spec，或等价的已确认业务行为与验收契约。

### 可选输入

- 最新需求和用户补充结论。
- API、WebSocket、事件和错误码契约。
- 风险说明、兼容性要求和历史问题。
- 当前代码与已有测试，仅用于确认可观察性、验证成本和重复覆盖。

事实优先级固定为：

1. 当前讨论中用户已经确认的结论。
2. 已确认 Spec 及其验收标准。
3. 最新接口或协议契约。
4. 当前代码和已有测试。

不得根据当前实现反推目标业务规则。代码、函数分支、已有 Mock 和旧测试不能覆盖已确认 Spec。输入缺失或互相矛盾时，先列出 `待确认`，不生成依赖这些决策的正式场景。

## 职责与非目标

### 负责

- 把每条验收标准映射为一个或多个测试场景。
- 补齐正常、异常、边界、权限、状态、竞态、一致性和生命周期风险。
- 设计必要的状态组合，但避免无业务差异的笛卡尔积。
- 用 Given / When / Then 写清业务条件、操作和预期结果。
- 标出优先级、建议验证方式、必要测试数据和可控外部条件。
- 发现 Spec 缺口、冲突或不可验证规则，并回流为待确认项。
- 为后续自动化测试保留稳定的场景编号和追踪关系。

### 不负责

- 重新决定产品行为、接口契约或前端架构。
- 按当前代码分支创造“偏门用例”。
- 编写测试代码、Mock 实现、测试辅助函数或框架配置。
- 决定 Vue 组件如何挂载、`vi.mock` 如何编写或断言 API 如何调用。
- 用覆盖率目标替代业务风险判断。
- 为了让现有实现易测而降低或改写业务预期。

## 核心工作流

### 1. 检查输入门槛

- 确认 Spec 状态、适用项目、版本和人工确认结果。
- Spec 尚未确认时，只输出缺口和待确认问题，不生成最终 Test Design。
- 确认目标范围及明确的非目标，避免测试设计扩张需求。

### 2. 提取业务验证模型

从 Spec 提取：

- 用户入口和可见结果。
- 状态、状态转换及合法组合。
- 关键身份标识、数据源和一致性规则。
- API、事件、错误和权限契约。
- 重试、超时、并发、乱序、恢复和清理规则。
- 验收标准、风险、兼容性和明确禁止行为。

只引用 Spec 中已有的架构边界，不在测试设计中重新展开实现方案。

### 3. 建立追踪矩阵

每条已确认验收标准必须映射到测试场景；一个场景也可以覆盖多个相互关联的规则，但必须写清关系。

推荐格式：

| Spec 来源 | 业务规则或风险 | 场景编号 | 优先级 | 建议验证方式 | 状态 |
| --- | --- | --- | --- | --- | --- |

`状态`只使用 `已确认` 或 `待确认`。待确认规则不能进入最终验收门槛。

### 4. 展开场景矩阵

按风险选择以下类别，不要求每个功能机械包含全部类别：

- 正常流程：核心用户目标能完成。
- 异常与失败：接口失败、无权限、无数据、不可恢复错误。
- 边界与无操作：空值、上下限、重复操作、非法状态、不应发生的副作用。
- 状态转换与组合：影响行为的状态及关键组合。
- 竞态与乱序：请求乱序、快速操作、对象切换、旧结果覆盖、重复事件。
- 数据一致性：页面、缓存、事件、服务端和持久化之间的一致性。
- 生命周期：初始化、刷新、重连、降级、取消、卸载和清理。
- 兼容性：历史数据、缺失字段、灰度或前后端上线顺序。

组合测试采用风险驱动：只有组合会改变业务结果、权限、数据源或恢复路径时才保留。

竞态场景应验证最终业务状态和不应发生的副作用，不能只验证回调或请求的执行顺序。

### 5. 编写业务场景

测试设计使用 `TS-<AREA>-<NNN>` 编号，避免和后续自动化测试用例编号混淆。

推荐模板：

```markdown
### TS-WS-001 WebSocket 连续重连失败后降级轮询

- 来源：Spec 验收标准 18
- 优先级：P0
- 建议验证方式：自动化验证（现有单元测试框架）
- 前置条件：用户已登录，初始连接失败
- Given：连续三次重连均失败
- When：第三次重连结束
- Then：实时状态进入 polling，并启动约定周期的 REST 刷新
- 不应发生：继续创建第四次重连或同时保留重连与轮询
- 所需可控条件：连接结果、计时推进
```

标题优先使用：

```text
[业务对象] + [条件] + [预期行为]
```

标题中的业务行为使用直白中文，避免“正确处理”“返回异常”之类模糊代称。技术对象存在明确类名时，可以使用类名辅助定位，但标题主体仍要表达业务条件和结果。

每个场景只验证一个业务结果，可以包含多个共同证明该结果的相关断言。决定分支和预期的状态、权限、数量、时间或类型必须显式出现在场景中。后续测试辅助构造只能隐藏固定路径、Token、通用初始化字段等不影响业务判断的数据，不能隐藏这些关键输入。

### 6. 建议验证方式

当前只使用两种方式：

- 自动化验证（现有单元测试框架）：无需真实浏览器、部署环境或多个真实服务，即可可靠模拟并断言的行为。包括纯规则、状态转换、Vue 组件交互和可见状态，以及在系统边界控制 API、WebSocket、时间、事件、持久化或跨模块协作的行为。
- 人工验证：现有单元测试环境无法可靠复现，必须依赖真实浏览器、部署环境或多个真实服务的行为。

组件测试可以使用现有单元测试运行器和工具完成，因此在流程上归入自动化验证，不再单独划分层级。第一版不要求接入集成测试或 E2E 工具；无法由现有单元测试框架可信模拟的内容暂列人工验证。

测试设计只说明需要控制的系统边界，不规定具体 Mock 写法。允许控制远端响应、落盘回调、调用参数或次数，以及竞态所需的时间和事件顺序；不得 Mock 被测模块的内部业务逻辑，也不得让 Mock 直接产出要验证的业务结果。后续自动化应遵守“Mock 系统边界，不 Mock 业务边界”。

### 7. 完成覆盖审计

- 每条已确认验收标准至少有一个场景。
- P0 风险包含成功和关键失败路径。
- 异步、缓存、对象切换或连续操作相关模块覆盖必要竞态。
- 多阶段流程验证影响后续行为的关键中间状态，不断言无关字段。
- 场景标题、输入和预期能够独立表达业务，不需要先读代码猜意图。
- 没有仅为覆盖函数分支、调用次数或覆盖率而存在的场景。
- 重复场景已经合并，保留的场景具有新增覆盖价值。
- 所有待确认项已列出，且没有混入正式验收门槛。

## 与其他 Skill 的边界

| Skill | 回答的问题 | 与本 Skill 的关系 |
| --- | --- | --- |
| `write-frontend-spec` | 做什么，行为和契约是什么 | 必要上游；提供已确认 Spec |
| `write-test-design` | 如何证明功能正确 | 当前 Skill；输出验证方案 |
| `write-unit-test` | 如何把测试设计实现为单测 | 可选下游；读取完整 Spec、完整 Test Design、代码和仓库测试规则 |

`write-test-design` 发现业务缺口时，应先回流 `write-frontend-spec` 或用户确认，不能在测试设计中静默补充需求。它只要求存在已确认 Spec 或等价契约，不要求当前项目已经安装 `write-frontend-spec` Skill。

`write-unit-test` 根据已确认的 Test Design 整体和现有业务代码生成单元测试。`TS-*` 是 Test Design 内的场景编号，只用于维护设计与单测实现之间的追踪关系，不表示一个场景必须对应一个测试文件或一个 `it`。一个场景可以拆成多个单测，多个相关场景也可以组织在同一 `describe` 中，但不得遗漏或擅自改写已确认的覆盖范围。

## 已确认的设计决策

1. 第一版只面向前端功能 Test Design，不扩展为通用后端或系统测试 Skill。
2. 最终 Test Design 必须以人工确认的 Spec 或等价契约为输入；未确认时只输出缺口清单。
3. 用户未指定文件名时，使用 `<feature>-test-design.md`，与对应 Spec 放在同一文档目录。
4. 优先级使用 `P0 / P1 / P2`，按业务影响划分，不套用固定场景数量。
5. 可以读取已有测试识别重复覆盖、可观察性和验证成本，但禁止从旧测试推导目标行为。
6. 验证方式只分为自动化验证和人工验证；当前不引入 E2E 等额外测试工具。
7. `write-unit-test` 是后续可独立设计的下游 Skill，不是本 Skill 的运行依赖。
