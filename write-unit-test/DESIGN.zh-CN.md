## 对话结论

推荐流程是：

```text
业务需求
↓
write-frontend-spec：定义做什么、行为契约和验收标准
↓
人工确认 Spec
↓
write-test-design：定义如何证明功能正确
↓
人工确认 Test Design
↓
编码实现
↓
write-unit-test：把 Test Design 中的自动化场景实现为单测
```

`write-unit-test` 不是根据当前代码分支补覆盖率，也不是只读取若干 `TS-*` 编号机械生成 `it`。它读取完整 Test Design，理解场景之间的业务关系，再结合现有代码、前端框架和仓库测试工具组织单测。

`TS-*` 是 Test Design 内的追踪编号：一个场景可以拆成多个单测，多个相关场景也可以放在同一测试文件或同一 `describe` 中。测试结构服从业务职责和被测模块边界，但不得遗漏、弱化或重新解释已确认场景。

## Skill 定位

`write-unit-test` 根据已确认的 Frontend Spec、已确认的 Test Design 和已经存在的业务代码，编写或补齐前端单元测试，并运行仓库已有测试工具完成验证。

第一版同时支持 Vue 和 React 前端单测，包括：

- 纯函数、状态模型和业务控制器测试。
- Vue 组件、Composable 和状态管理测试。
- React 组件、Hook 和状态管理测试。
- 通过 Mock 系统边界模拟 API、WebSocket、时间、事件和持久化的协作测试。

不负责真实浏览器、部署环境、多服务联调或 E2E 测试。

## 输入与事实来源

### 必需输入

- 已确认的 Frontend Spec 或等价业务契约。
- 已确认的 Test Design。
- 已存在的目标业务代码。
- 仓库现有测试框架、命令和工程约定。

### 可选输入

- 用户指定的测试文件、模块或场景范围。
- 已有单测、测试辅助函数、Mock 和历史失败记录。
- 覆盖率报告、CI 日志或评审意见。

事实优先级固定为：

1. 当前讨论中用户已经确认的结论。
2. 已确认 Spec。
3. 已确认 Test Design。
4. 当前仓库测试规则和业务代码。
5. 已有测试与历史行为。

Spec 与 Test Design 冲突时，以 Spec 为准并回流修正 Test Design。代码或旧测试与已确认行为冲突时，不得通过改弱断言、增加特殊 Mock 或改写预期让测试通过。

## 固定规则与仓库适配

Skill 固定以下跨仓库规则：

- 测试名称描述的业务行为必须通过被测入口调用真实业务函数产生。
- 只 Mock 系统边界，不 Mock 被测业务逻辑，也不允许 Mock 直接模拟业务结果。
- 决定业务分支或预期结果的参数必须在用例内显式传入。
- 测试标题固定使用 `[TS-*] + 中文业务标题`。
- 每个测试文件固定只有一个文件级父 `describe`，父级下保留业务子分组。
- 自动化、人工验证、本次范围外和阻塞场景必须保持可追踪。
- 测试通过且没有本次引入的 warning、资源泄漏或残留 Mock 才算完成。

仓库负责提供可变的实现条件：

- Vue 或 React，以及当前使用的状态管理方案。
- Vitest、Jest 或其他现有测试运行器。
- Vue Test Utils、Testing Library 或其他现有组件测试工具。
- 测试文件位置、文件后缀、运行命令、DOM 环境和已有测试辅助函数。

仓库条件只决定如何落地，不得静默削弱 Skill 固定规则。仓库显式规则与固定规则冲突时，记录冲突和影响并询问用户，不自行选择一方覆盖另一方。

## 职责与非目标

### 负责

- 识别 Test Design 中标为自动化验证的全部场景。
- 检查场景、业务代码、测试文件和可观察结果之间的对应关系。
- 按模块职责选择可信的单测边界和测试文件位置。
- 编写测试用例、必要的系统边界 Mock、测试数据和辅助函数。
- 覆盖正常、失败、边界、状态、竞态、一致性和生命周期场景。
- 运行目标测试，修复本次测试代码造成的失败、警告、计时器泄漏和未清理 Mock。
- 生成 `<feature>-unit-test-report.md`，记录实现映射、执行结果和阻塞项。

### 不负责

- 重新决定产品行为、接口契约、架构或测试范围。
- 为当前实现分支创造 Test Design 中不存在且无业务价值的用例。
- 实现 Test Design 中标为人工验证的场景。
- 引入 E2E、真实浏览器或真实服务测试工具。
- 用覆盖率百分比替代业务场景覆盖。
- 为通过测试而 Mock 被测业务逻辑、跳过失败场景或降低断言强度。
- 未经用户授权修改生产代码、依赖或测试框架配置。

## 核心工作流

### 1. 检查输入门槛

- 确认 Spec 和 Test Design 已经人工确认，目标代码已经存在。
- 读取完整 Test Design，包括目标、非目标、风险、追踪矩阵、全部场景、测试数据、可控条件、人工验证项和待确认项。
- 在保留完整场景清单的前提下，提取本次范围内标为自动化验证的 `TS-*` 场景；人工验证项和本次范围外场景只记录，不生成单测。
- 明确用户要求的范围。用户未缩小范围时，默认覆盖 Test Design 中全部自动化场景；缩小范围时记录排除理由，不能把范围外场景误报为阻塞或静默删除。
- 输入缺失、场景仍待确认或实现尚不存在时，列出阻塞项，不自行补充业务规则。

### 2. 读取仓库工具与约定

检查：

- `AGENTS.md`、项目说明和测试目录约定。
- `package.json` 或等价脚本中的测试命令。
- 测试框架、组件挂载工具、DOM 环境和覆盖率配置。
- 相邻测试的命名、`describe` 层级、Mock、stub 和辅助函数用法。
- 是否已有可复用的测试工厂、固定数据和边界适配器。

使用当前仓库已有工具和组织方式，不为了个人偏好重排无关测试或引入平行辅助工具。仓库约定只能补充实现细节，不能覆盖上节固定规则。

复杂路径可以在 `$feature-architecture-recon` 已可用时辅助调查，但它不是运行依赖，也不得自动安装。无论是否使用该 Skill，都必须完成足够的目标代码追踪。

### 3. 追踪实现和可观察结果

针对每个场景追踪：

```text
用户操作或外部事件
→ 入口方法或组件
→ 状态与业务判断
→ 系统边界或副作用
→ 用户可见结果或最终业务状态
```

确认：

- 被测职责属于哪个模块。
- 哪些状态和输入决定分支。
- 哪些系统边界需要控制。
- 哪些结果可以从公开行为观察。
- 哪些关键中间状态会影响后续行为。
- 是否存在竞态、迟到结果、定时器或卸载清理。

不要把私有方法调用次数当作主要业务结果。只有调用本身属于外部契约或用于证明必要副作用时才断言。

### 4. 建立实现映射

在修改测试前，先逐条核对 Spec 规则仍有 Test Design 场景承接，再把实现映射写入 `<feature>-unit-test-report.md`：

| Spec 来源 | 业务规则或风险 | 优先级 | TS 场景 | 验证方式 | 测试文件 | 业务分组 / 计划用例 | 主要验证点 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

`状态`建议使用：

- `待实现`
- `已覆盖`
- `阻塞`
- `人工验证，不实现`
- `本次范围外`

已有单测只有在业务条件和预期均等价时才能计入覆盖。不能因为执行了相同函数或分支就认定场景已覆盖。

### 5. 编写单测

- 测试标题使用直白中文，表达业务条件和预期结果。
- 测试标题固定以对应的 `[TS-*]` 开头。
- 每个用例证明一个业务结果；可以包含多个共同证明该结果的断言。
- 测试名称描述的业务行为必须通过被测入口调用真实业务函数产生。
- 单测参数保持“所见即所得”：影响业务分支或预期结果的状态、权限、数量、时间和类型必须在用例内显式传入，不得藏在辅助函数的默认参数中。
- 固定路径、Token、通用初始化等与业务判断无关的数据可以由构造函数统一生成。
- Mock 只用于远端响应或落盘回调、验证系统边界调用参数或次数，以及控制竞态所需的时间或事件顺序；Mock 内不得模拟业务结果。
- 竞态测试控制时间和事件顺序，并断言最终业务状态与不应发生的副作用。
- 多阶段行为验证必要的关键中间状态，不断言无关实现细节。
- 优先复用仓库已有测试工具；新增辅助函数时保持职责单一、命名清楚。
- 不得为了减少用例数，把多个独立业务结果塞进一个难以定位失败原因的测试。

### 6. 运行和修正

按以下顺序验证：

1. 运行新增或修改的目标测试文件。
2. 运行直接相关模块的测试。
3. 按仓库要求运行更大范围的测试、类型检查或构建。
4. 检查退出码、失败详情、stderr、warning、未处理 Promise、未清理计时器和残留 Mock。

测试退出码为 0 但产生本次改动相关警告，仍视为未完成。不得盲目更新快照、增加重试或放宽等待时间掩盖不稳定问题。

## 测试组织与追踪

测试文件按被测模块和业务职责组织，不按 `TS-*` 一对一创建文件。

每个测试文件固定使用以下结构：

```text
<目标模块>
└─ 一个文件级父 describe
   ├─ 正常流程
   ├─ 异常与权限
   ├─ 状态与竞态
   └─ 生命周期与清理
```

已有测试文件存在多个顶层 `describe` 时，增加一个文件级父 `describe`，保留原有业务子分组，不把所有用例扁平化。

测试标题固定使用 `[TS-AREA-NNN] + 中文业务标题`，例如：

```ts
it('[TS-WS-001] 连续三次重连失败后切换为轮询', async () => {})
```

这样测试失败日志可以直接反查 Test Design。相关场景可以共享测试文件、`describe`、setup 和辅助函数，但默认分别编写能够独立定位失败原因的测试。只有多个 `TS-*` 实际共同证明同一个业务结果时才允许共用一个测试，并在标题中列出全部编号。一个场景拆成多个测试时复用同一编号并用标题区分验证点。

## Mock 与测试数据

遵守“Mock 系统边界，不 Mock 业务边界”：

### 仅允许控制

- API、WebSocket 等远端响应，以及落盘回调的成功、失败、超时和乱序。
- 系统边界的调用参数、调用次数和取消行为，但只在这些调用本身属于待验证契约时使用。
- 系统时间、定时器和事件到达顺序，用于控制竞态时序。

### 不得控制

- 被测模块内部的状态合并、权限判断、重试决策或业务映射。
- 直接把最终业务结果写入 Store、组件状态或返回值的 Mock。
- 为命中特定分支而构造 Test Design 未定义的私有实现条件。

### 参数可见性

- 决定业务分支或预期结果的参数必须在用例内显式传入。
- 测试辅助函数不得为关键参数提供隐藏默认值。
- 固定路径、Token 和通用初始化等无关数据可以统一生成，以减少重复。

每个测试结束后恢复 fake timers、全局对象、Mock、订阅和挂载组件，避免用例之间相互污染。

## 生产代码边界

默认只修改测试代码。

如果出现以下情况，应停止扩张改动并向用户说明：

- 生产代码行为与已确认 Spec 或 Test Design 冲突。
- 必须调整生产代码结构才能从可信边界验证目标行为。
- 当前测试工具无法模拟已确认的自动化场景。
- 需要新增依赖、测试环境或全局配置。

不得通过 Mock 内部业务逻辑、使用 `.skip`、删除断言或接受错误结果绕过问题。出现冲突时，在 `<feature>-unit-test-report.md` 中记录 `场景 → 代码证据 → 预期结果 → 实际结果 → 所需改动`，将状态标为 `阻塞`，再询问用户是否授权修改生产代码或调整工具链。

## 验证与交付

在 Test Design 同一目录固定创建 `<feature>-unit-test-report.md`。该文件在编写单测前建立，在验证后更新最终状态，不修改已经确认的 Test Design。

实施记录包含：

1. Spec、Test Design、项目和本次范围。
2. `Spec → TS-* → 测试文件 → 测试用例 → 结果` 实现映射。
3. 新增或修改的测试文件。
4. 实际运行的命令、结果和 warning 检查。
5. 人工验证、本次范围外和阻塞场景。
6. 生产代码、依赖或测试配置是否发生变化。

完成门槛：

- 本次确认范围内的每个自动化场景均为 `已覆盖` 或有明确 `阻塞` 原因。
- 完整 Test Design 清单仍然可见，人工验证项和本次范围外场景均保留状态及理由。
- 每个已覆盖场景能够反查到具体测试文件和测试用例。
- `<feature>-unit-test-report.md` 已更新为最终状态。
- 人工验证场景没有被伪装成单测。
- 新增测试验证业务行为，而不是仅验证函数执行和分支命中。
- Mock 没有直接产出被断言的业务结果。
- 竞态、生命周期和错误路径没有计时器、订阅或全局状态泄漏。
- 目标测试和仓库要求的相关检查通过，且没有本次引入的 warning。
- 未经授权没有修改生产代码、依赖和配置。

最终回复给出实施记录路径、修改的测试文件、验证结果和仍处于 `阻塞` 的场景。

| --- | --- | --- |
| `write-frontend-spec` | 功能做什么，行为契约是什么 | 上游事实来源，不要求当前环境安装该 Skill |

缺少某个上游 Skill 不等于无法执行；只要对应的已确认 Spec、Test Design 和业务代码存在即可。不得自动安装、链接或复制其他 Skill。

## 已确认的设计决策

1. **适用范围**：第一版面向 Vue 和 React 前端单元测试，不扩展到后端、E2E 或真实服务测试。
2. **执行时机**：在业务代码存在且 Test Design 已确认后执行，第一版不支持 TDD 流程。
3. **场景编号位置**：测试标题固定使用 `[TS-*] + 中文业务标题`。
4. **生产代码冲突**：默认不修改生产代码；在实施记录中保留证据并标为 `阻塞`，再询问是否授权修复。
5. **可测性重构**：与业务修复一样需要用户授权，不能为完成单测静默调整生产代码结构。
6. **依赖与配置**：不得自动引入新测试框架、E2E 工具或全局配置；确有必要时先询问。
7. **验证范围**：至少运行目标测试和直接相关模块测试；更大范围检查遵守仓库约定和改动风险。
8. **人工验证项**：只在实施记录中保留，不生成 `.skip`、占位测试或伪自动化用例。
9. **实施记录**：固定生成 `<feature>-unit-test-report.md`，与 Test Design 放在同一目录。
10. **规则分层**：Skill 固定业务测试原则，仓库只提供框架、工具和组织方式等适配信息。
11. **测试组织**：每个测试文件固定只有一个文件级父 `describe`，并保留业务子分组。
12. **用例真实性**：业务结果必须经过真实函数逻辑；Mock 范围受限；关键参数必须所见即所得。
