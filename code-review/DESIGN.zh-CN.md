## Skill 定位

`code-review` 用于按照已确认的目标审查当前代码改动，直接解决范围内的 P0、P1 问题，并把 P2、P3 等非阻塞问题一次性汇总给用户。

它不是只输出评论的静态 Review。调用该 Skill 意味着允许 Codex 在用户给定的代码范围内：

- 查明问题的真实调用路径和影响。
- 修复能够确定的 P0、P1 问题。
- 补充或调整与修复直接相关的单元测试。
- 运行与风险匹配的验证。
- 停止继续打磨 P2、P3，避免陷入无止境的 Review 循环。

Skill 的核心原则是：

```text
先确定评审基准和范围
→ 用代码证据识别问题
→ 修复并验证 P0/P1
→ 复查修复路径是否仍有 P0/P1
→ 汇总 P2/P3 后停止
```

## 输入与评审基准

### 模式 A：调用时引入了 Spec Markdown

如果用户在调用 Skill 时附带、点名或提供了作为实现依据的 `spec.md`、`*-spec.md` 或其他明确声明为 Spec 的 Markdown 文件，则必须完整读取该 Spec，并据此 Review 代码。

需要从 Spec 中提取：

- 目标与非目标。
- 用户可见行为。
- 数据来源、状态归属和接口契约。
- 成功、失败、取消、并发和恢复规则。
- 验收标准与明确禁止项。
- 尚未确认或明确排除的内容。

只有已确认的规则可以作为缺陷判断依据。Spec 中的待确认项、建议项或未来范围不能被当成 P0/P1。

如果当前调用同时明确修改了 Spec 中的某条规则，以用户本次明确指令为准，并在 Review 结果中说明与 Spec 的差异；不得静默选择其中一方。

普通 README、设计背景或与任务无关的 Markdown 不因为扩展名是 `.md` 就自动成为评审基准。

### 模式 B：没有引入 Spec Markdown

如果没有作为实现依据引入 Markdown Spec，则使用当前会话中已经明确的执行思路作为 Review 基准，包括：

- 用户明确要求实现的行为。
- 用户已经确认的方案和边界。
- 用户明确否定的方案。
- 当前会话中已经达成一致的取舍和停止条件。

Codex 自己提出但尚未得到用户确认的建议，不能自动升级为评审基准。

如果既没有 Spec，也没有当前会话中明确的执行思路，Skill 应先说明缺少判断基准并请求补充，不得仅凭个人偏好把代码风格问题标成 P0/P1。

### 单元测试评审基准：已确认 Test Design

如果用户在调用 Skill 时附带、点名或提供了由 `write-test-design` 生成的 `*-test-design.md`，且该 Test Design 已经确认，则必须完整读取，并作为单元测试专项评审的覆盖基准。

需要从 Test Design 中提取：

- `TS-*` 场景编号、来源、优先级和确认状态。
- Given / When / Then、不应发生的副作用和所需可控条件。
- 建议验证方式及并发、乱序、状态覆盖和清理要求。
- Spec、测试场景和现有单元测试之间的追踪关系。

Test Design 用于定义如何证明已确认行为，不替代 Spec 对业务行为和契约的定义。只有标为 `已确认` 且建议采用 `自动化验证（现有单元测试框架）` 的场景，才能作为单元测试覆盖要求；`待确认` 或 `人工验证` 场景不能被当成缺少单元测试的 P0/P1。如果 Test Design 与已确认 Spec 冲突，应以 Spec 为准并报告冲突，不得静默选择其中一方。

### 事实来源顺序

发生冲突时按以下顺序判断：

1. 当前调用中用户的明确指令。
2. 当前会话中用户已经确认的结论。
3. 本次引入且已确认的 Spec。
4. 本次引入且已确认的 Test Design。
5. 仓库规则、接口契约和测试约定。
6. 当前代码、运行结果和历史测试所反映的现状。

现状代码用于证明实现行为，不得反过来覆盖已经确认的目标行为。

## 评审范围

按以下顺序确定 Review 范围：

1. 用户明确点名的文件、目录、提交、PR 或 diff。
2. 当前会话中为了同一任务新增或修改的文件。
3. 与上述改动直接关联的调用者、消费者、类型、接口和单元测试文件。

如果用户没有指定范围，应检查 `git status`、暂存区 diff 和工作区 diff，识别当前任务相关文件；不得把脏工作区中不相关的用户改动擅自纳入修复。

每个范围内文件都要读取足够的上下文，不能只看 diff 行。至少确认：

- 入口和调用者。
- 输入来源和输出消费者。
- 状态或持久化事实源。
- 错误、清理和并发路径。
- 相关类型和单元测试。

Review 可以为了确认影响读取范围外文件，但修复不得扩展到无关代码。

## 问题优先级与收敛规则

### P0：立即阻断

包括但不限于：

- 可到达的数据永久丢失、不可恢复覆盖或严重安全问题。
- 核心功能整体不可用、应用无法启动或生产级崩溃。
- 会造成大范围错误结果且没有有效兜底。

### P1：必须在本轮解决

包括但不限于：

- 明确违反已确认 Spec 或当前执行思路的核心行为。
- 正常主路径或重要失败路径不可用。
- API、持久化、进程间通信或状态契约不一致。
- 并发、乱序、重试、清理或鉴权逻辑会错误覆盖有效状态。
- 当前改动引入确定的回归、构建失败、类型错误或相关测试失败。
- 错误处理吞掉关键失败，导致系统继续以错误状态运行。

### P2：有价值但不阻塞

包括但不限于：

- 低频边界条件缺失，但不会破坏核心流程。
- 不必要的提前抽象、函数拆分过细或明显增加阅读成本。
- 单测结构、命名、重复和可维护性问题，但断言仍能正确保护业务。
- 有实际维护成本，但不需要阻塞当前交付的问题。

### P3：建议与风格

包括命名润色、注释表达、格式统一和不影响理解及行为的局部风格问题。

### 证据要求

每个问题必须能够说明：

```text
触发条件 → 实际代码路径 → 错误结果 → 影响范围
```

仅凭“可能”“也许”或个人偏好不能标成 P0/P1。无法确认的问题应继续做只读验证；仍无法确认时列为待验证项，不得为了显得完整而提高优先级。

### 收敛规则

- 发现 P0/P1 后直接做范围内的最小修复，并运行相关验证。
- 修复后只复查受影响路径及新 diff，确认没有残留或新引入的 P0/P1。
- P0/P1 可以继续迭代，直到解决或遇到确实需要用户决策、额外权限、外部系统的阻塞。
- P2、P3 不触发下一轮修复和全量复查，只在最终结果中一次性汇总。
- 不得因为仍能发现新的命名、抽象或测试风格建议而继续循环。

## 固定评审规则

### 1. 纯类型导入必须使用 `import type`

TypeScript 中只用于类型位置的 `interface`、`type` 或其他类型符号必须使用类型导入：

```ts
import type { IRequestConfigIdentity } from "./globalConfig";
```

同一模块同时导入运行时值和类型时使用内联类型标记：

```ts
import { mapRemoteTaskStatus, type IRequestConfigIdentity } from "./module";
```

不得把运行时需要的枚举、函数、常量或类错误改成类型导入。

使用 `import type` 的原因是明确保证该依赖在编译后被删除，不触发目标模块求值，从而降低：

- 运行时循环依赖风险。
- 无意义的模块加载。
- 模块顶层副作用被意外执行的风险。
- 对 TypeScript import elision 配置或其他转译工具行为的依赖。

这是 Skill 的明确强制规则。范围内发现纯类型普通导入时，直接进行局部机械修正，不把它留到 P2 循环；但如果符号存在运行时用途，必须保留普通导入。

### 2. 每个文件检查是否拆分过细

对每个 Review 范围内的文件，检查本次新增、提取或明显受改动影响的函数。

强制检查信号是：当前函数是否只包含一个逻辑动作。如果是，必须继续判断这个函数是否有独立存在的必要，而不是默认“单一职责”就代表拆分合理。

以下情况通常值得保留：

- 封装稳定且重复出现的业务规则。
- 隔离文件、网络、IPC、数据库或第三方服务等系统边界。
- 明确事务、文件锁、权限、错误转换、资源清理等关键边界。
- 函数名能够显著降低主流程理解成本。
- 已有多个真实调用点，或者项目本身已经采用相同抽象方式。

以下情况通常属于拆分过细：

- 仅被调用一次，只包装一条赋值、一次转发或一个简单判断。
- 没有独立业务含义，也没有边界、复用或错误处理价值。
- 阅读主流程时必须频繁跳转，合并后反而更容易顺序理解。
- 只是预判未来可能复用，当前没有实际需求。
- 只是为了让单元测试更容易 Mock 或直接调用。

“函数只有一个逻辑”是必要性检查的触发条件，不是自动合并条件。最终必须给出 `保留`、`建议内联` 或 `需要调整边界` 的结论和具体理由。

一般情况下，纯阅读成本问题记为 P2；如果过度拆分导致顺序、锁、事务、错误处理或状态边界实际错误，则按真实影响提高到 P1。

### 3. 保持实现边界直白

Review 还需检查：

- 是否为简单改动新增无必要的 helper、manager、adapter、strategy 或多层包装。
- 是否把协议处理、API 适配和业务判断放错层。
- 是否出现为了“统一”而让主流程需要跳转多层才能理解。
- 是否重复保存同一状态、形成多个事实源或只同步磁盘却没有同步运行时缓存。
- 是否引入没有消费者的字段、Promise、状态或返回值。

抽象必须能够用一句话说明它减少了什么真实重复或错误风险；说不清时优先保持 inline。

### 4. 并发与状态一致性

涉及异步、文件、缓存、Worker、IPC 或多进程时，必须区分：

- 文件锁只保护临界区，是否真的同步了其他进程的内存状态。
- 请求开始时的快照与响应到达时的最新状态是否混用。
- 旧请求失败是否会覆盖新请求成功结果。
- 落盘状态、当前进程缓存和其他进程缓存是否一致。
- 初始化、保存、清理失败后是否留下半完成状态。

不能因为加了锁就默认并发问题已经解决，必须说明锁保护的对象和未覆盖的状态。

### 5. 最小改动与用户工作区保护

- 只修复 Review 范围内可确认的 P0/P1和明确的 `import type` 规则。
- 不重排、格式化或清理无关文件。
- 不覆盖用户已有改动，不使用破坏性 Git 命令。
- P2/P3 默认只报告，不顺手扩大重构。

## 单元测试专项评审

当实现包含单元测试，或者仓库中存在与目标代码直接相关的单元测试文件时，必须执行本节；不能因为测试文件本次没有修改就跳过。

### 1. 业务代码不能让步于测试便利性

检查生产代码是否仅为方便单测而增加了业务不需要的结构，例如：

- 只为等待测试而增加的 Promise、延时或回调。
- 只为断言或 Mock 而增加的字段、返回值或公开方法。
- 只为测试导出的内部实现。
- 生产环境没有意义的开关、分支或依赖注入包装。
- 为命中特定分支而拆出的单次调用 helper。

判断问题时必须回答：该结构在没有单元测试时，是否仍然改善真实业务契约、运行时边界或代码可读性？

- 如果答案是否定的，应优先让测试通过真实入口观察结果或 Mock 系统边界。
- 如果该结构改变生产行为、公开契约或错误时序，按影响标为 P1 并修复。
- 如果行为正确但增加阅读和维护成本，列为 P2，不为此启动新一轮重构。

不得为了测试方便牺牲实际业务代码的清晰度和正确性。

### 2. 再检查单元测试自身逻辑

相关测试文件必须检查：

- 测试标题、前置条件、调用入口和断言结果是否表达同一业务行为。
- 被测业务结果是否经过真实业务函数产生，而不是由 Mock 直接返回最终结果。
- 是否只 Mock 网络、文件、时间、Worker、IPC 等系统边界。
- 决定业务分支的参数是否在用例中明确可见，没有藏在 helper 默认值里。
- Promise 是否正确等待，异常断言是否真的覆盖失败路径。
- fake timers、全局对象、订阅、组件和 Mock 是否在用例后恢复。
- 是否存在永远不会失败、只验证 Mock 自己、断言错误对象或断言无关实现细节的测试。
- 对能够由现有单元测试框架稳定控制的并发、乱序和状态覆盖场景，是否存在相应回归测试；缺失且与本次 P0/P1 修复直接相关时，必须补充测试。
- 引入已确认 Test Design 时，范围内标为自动化验证的 `TS-*` 是否都有可追踪的单元测试；人工验证和待确认场景不得强制转成单元测试。
- 是否遗漏与本次 P0/P1 修复直接相关的回归场景。
- 测试是否引入 warning、未处理 Promise、资源泄漏或顺序依赖。

已有测试不能只因为“通过”就视为正确。必须确认它能够在业务代码错误时失败，并且失败原因指向真实业务结果。

### 3. 测试修复边界

- P0/P1 修复涉及已有测试基础设施时，补充或调整必要的回归测试。
- 不为了提高覆盖率创建没有业务价值的测试。
- 不通过降低断言、扩大 Mock、增加无意义重试或 `.skip` 让测试变绿。
- 如果修复需要新增依赖、改变测试框架或大范围调整生产代码，应先报告阻塞并请求用户授权。

## 工作流

### 第一步：确定基准和范围

1. 判断是否引入了作为实现依据的 Spec Markdown，以及是否引入了已确认 Test Design。
2. 有 Spec 或 Test Design 时按各自职责完整读取；无 Spec 时提取当前会话中用户已确认的执行思路。
3. 确定目标 diff、文件和直接关联测试。
4. 读取仓库规则和目标文件上下文。

### 第二步：建立实现证据链

围绕目标行为追踪：

```text
入口/事件
→ 参数与状态来源
→ 核心判断
→ API、持久化或进程边界
→ 消费者
→ 用户可见结果或最终状态
```

优先核对真实请求路径、落盘字段、缓存状态、调用者、消费者、diff 和测试结果，不以猜测替代代码证据。

### 第三步：逐文件 Review

每个文件至少检查：

1. 是否符合 Spec 或当前执行思路。
2. 正常、失败、清理和并发路径是否正确。
3. 类型、接口和运行时导入是否正确，纯类型是否使用 `import type`。
4. 每个新增或受影响函数是否只包含一个逻辑，以及是否拆分过细。
5. 是否存在无消费者字段、重复状态或测试专用生产结构。
6. 是否存在相关单元测试，测试逻辑是否可信。

### 第四步：修复 P0/P1

1. 先记录可复现路径和影响。
2. 做最小、局部、符合现有代码风格的修复。
3. 同步调整与修复直接相关的测试。
4. 不顺手重构 P2/P3。

### 第五步：验证并复查

按风险选择并记录：

- 目标测试文件。
- 直接相关模块测试。
- 类型检查、Lint、构建或静态检查。
- diff、行尾、生成文件和无关改动检查。

如果更大范围检查因仓库已有问题失败，应区分本次新增错误与基线错误。测试退出码为 0 但出现本次引入的 warning、未处理 Promise 或资源泄漏，仍不能算完成。

验证后只复查 P0/P1 修复路径和新 diff。确认没有 P0/P1 后进入最终汇总，不再为 P2/P3 开启下一轮。

## 输出格式

最终输出优先给结论，再给证据。

### 1. Review 结果

- 是否存在 P0/P1。
- 已修复数量、阻塞数量。
- 使用的评审基准：Spec 路径或当前会话确认结论。

### 2. P0/P1 修复清单

| 优先级 | 问题与触发条件 | 影响 | 修复 | 文件 | 验证 |
| --- | --- | --- | --- | --- | --- |

如果没有，明确写 `未发现 P0/P1`。

### 3. P0/P1 阻塞项

只有确实需要用户决策、额外授权或外部环境时才列出，并说明已经完成的验证和最小所需输入。

### 4. P2/P3 遗留总结

| 优先级 | 问题 | 影响 | 建议 | 文件位置 |
| --- | --- | --- | --- | --- |

## 完成标准

一次 Review 完成必须满足：

- 评审基准明确：已读取 Spec，或已提取当前会话中的明确执行思路。
- Review 范围明确，没有误改不相关的用户工作区内容。
- 每个发现都有触发条件、代码路径、错误结果和影响证据。
- 所有可在当前授权范围内解决的 P0/P1 已修复并验证。
- 未解决的 P0/P1 只有真实阻塞，并清楚说明所需决策或权限。
- 纯类型导入已按明确规则使用 `import type`，没有误改运行时导入。
- 每个范围内文件都完成拆分过细检查并给出理由。
- 存在相关单元测试时，已检查生产代码是否为测试让步，也已检查测试自身逻辑。
- 引入已确认 Test Design 时，已检查范围内自动化 `TS-*` 的单元测试追踪关系，没有把人工验证或待确认场景误列为缺陷。
- P2/P3 已一次性汇总，没有因此进入新一轮修改循环。
- 相关测试和静态检查已运行，或明确说明无法运行的客观原因。
- 最终 diff 不包含无关格式化、生成文件或用户未授权的扩展改动。

## 非目标与边界

本 Skill 不负责：

- 在没有 Spec 或明确执行思路时替用户发明需求。
- 自动修复所有 P2/P3 或进行“顺手重构”。
- 为追求零建议而反复 Review 整个仓库。
- 把个人代码风格偏好包装成高优先级缺陷。
- 只为了单测方便修改生产接口、依赖、框架或全局配置。
- 用文件锁、Mock、类型断言或测试通过掩盖未解决的运行时状态问题。
- 未经用户授权提交、推送、创建 PR 或修改范围外文件。
