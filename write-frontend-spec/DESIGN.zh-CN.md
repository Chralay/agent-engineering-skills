# write-frontend-spec 设计说明

这个文件面向使用者，解释 Skill 的目标和设计取舍。Codex 执行时以 `SKILL.md` 为准。

## 为什么需要这个 Skill

前端 Spec 容易出现四类问题：

- 只复述需求，没有核对当前代码和真实接口。
- 页面行为、数据契约和异常分支分散，开发时仍要重新做决策。
- 同一流程在多个章节重复描述，修改后互相矛盾。
- 验收标准只写“功能正常”，无法据此测试。

这个 Skill 用来把需求、用户确认、当前代码和前后端契约整理成一份可直接实现、可明确验收的前端 Spec。

## 适用边界

适合以下任务：

- 新写前端 Spec 或技术方案。
- 把已有需求整理成可实现的前端契约。
- 按统一目录重构现有方案。
- 对照当前代码检查 Spec 是否遗漏或过时。

默认只交付 Spec，不自动进入编码。业务字段和流程必须来自当前项目，不把“任务插队”的具体规则固化为通用模板。

## 核心设计

### 1. 证据有优先级

发生冲突时，按以下顺序判断：

1. 当前讨论中用户已经确认的结论。
2. 最新需求、接口或协议。
3. 当前代码和运行行为。
4. 旧方案和旧假设。

不能确认且会改变方案的内容，要先提问；不影响主方案的小问题，采用最小假设并写明。

每条强制规则都应能归入 `用户已确认`、`需求或接口已定义`、`代码已验证` 或 `待确认`。没有实际读取代码时，不能写成“当前代码已经如此”；需求没有提到的状态，也不能直接解释为“不支持”。

资料不完整时，输出应明确分成 `已确认`、`建议默认值（待确认）` 和 `待确认`。常见 UX 只能作为建议，不能直接写成正式规则或验收项。

### 2. 复杂功能先判断是否需要架构侦察

以下任一情况成立时，应把功能视为复杂：

- 跨越多个前端、服务、后端或持久化边界。
- 状态归属、身份标识、事实源或实际运行路径不清楚。
- 涉及异步任务、WebSocket、重试、并发、恢复或清理。
- 常规代码追踪不足以可靠确认当前行为。

复杂功能需要先判断当前会话是否可使用 `$feature-architecture-recon`：

1. Skill 可用时，先用它梳理当前流程、事实源、不变量、失败路径和证据链。
2. Skill 不可用时，先询问用户是否引入，不得自动安装、关联或复制。
3. 用户同意时，按用户批准的方式引入并完成侦察，再继续编写 Spec。
4. 用户不同意时，使用 `write-frontend-spec` 内置的最小代码追踪流程继续，并明确证据范围和剩余未知项。

简单功能、全新功能或现状已经验证完整时，可以跳过。用户默认只需调用 `$write-frontend-spec`；架构侦察只提供现状证据，不能替代目标业务决策。

### 3. 默认使用十段式目录

```text
目标 / 非目标
现状与问题
架构图与流程图
关键数据结构
上下游依赖
关键假设与约束
接口
Trade-off
验收标准
风险、兼容性
```

这套顺序先固定范围，再说明证据和设计，最后落到验收与风险。章节确实不适用时可以省略，但不能用省略章节来隐藏未澄清的问题。

### 4. 同一规则只完整描述一次

复杂流程、并发规则或状态映射应放在一个主章节中完整定义。其他章节通过锚点引用，不再复制一遍。

- `关键假设与约束`、`接口`负责定义规则。
- `验收标准`负责验证规则，不重新发明规则。
- `现状与问题`只写当前事实，不混入目标设计。

### 5. 同时写清行为和契约

Spec 不能只写接口，也不能只写页面。重要流程需要同时覆盖：

- 用户看到什么、能做什么。
- 前端以哪个字段或快照为准。
- 请求、响应、事件和错误如何解释。
- loading、禁用、空数据、失败、重试和清理如何处理。
- 并发、乱序、幂等或历史兼容由哪一端负责。

批量处理、部分失败、刷新时机、选择保留、重试策略和请求形态都属于会改变实现的决策。来源没有定义时，应先列为待确认，不能套用常见做法补齐。

### 6. 保持简洁、精确

优先使用：

- 表格：现状、映射、依赖、错误码、取舍。
- Mermaid：跨组件、分支较多或有明确时序的流程。
- TypeScript / JSON：需要逐字段确认的契约。
- 明确措辞：`必须`、`只`、`不得`、`失败时保留`。

避免使用“适当处理”“按需刷新”“保持兼容”这类无法直接实现或验收的表达。

## 推荐工作流

```text
读取最新需求和用户确认
↓
判断是否需要架构侦察；复杂且 Skill 不可用时先询问用户
↓
核对当前代码、接口和真实数据来源
↓
锁定范围、状态、标识、异常和系统边界
↓
按十段式目录编写 Spec
↓
检查单一事实源、交叉引用和契约一致性
↓
校验文档结构并执行 git diff --check
```

## 完成标准

一份合格的输出应满足：

- 开发者无需重新猜测关键行为。
- 页面行为和接口语义能一一对应。
- 复杂流程包含成功、失败和边界状态。
- 验收项可以观察或测试，并包含关键反例。
- 未确认的决策不进入正式验收项。
- 每条强制规则都有来源，缺失决策明确标为待确认。
- 复杂功能经过架构侦察门槛，不会静默引入其他 Skill。
- 文档没有互相冲突的重复定义。
- 没有无依据的字段、迁移、兜底或未来范围。
