# write-frontend-spec 设计说明

这个文件面向使用者，解释 Skill 的目标和设计取舍。Codex 执行时以 `SKILL.md` 为准。

## 为什么需要这个 Skill

前端 Spec 的常见问题包括：

- 只复述需求，没有核对当前代码和真实接口。
- 在术语、交互和生命周期还未确认时过早写成可直接实施的完整方案，后续一个业务决定变化会连带修改多个章节。
- Skill 把常见 UX 或参考项目行为直接补成正式交互，使用者只能在长篇 Spec 中逐项发现并纠正。
- 页面行为、数据契约和异常分支分散，开发时仍要重新做决策。
- 同一流程在多个章节重复描述，修改后互相矛盾。
- 验收标准只写“功能正常”，无法据此测试。

这个 Skill 用来把需求、用户确认、当前代码和前后端契约整理成一份可直接实现、可明确验收的前端 Spec。

## 适用边界

适合以下任务：

- 新写前端 Spec 或技术方案。
- 把已有需求整理成可实现的前端契约。
- 按统一目录重构现有方案。
- 对照当前代码检查 Spec 是否遗漏或过时。
- 根据 Review 结论修改已有 Spec，并检查受影响章节是否一致。

默认只交付 Spec，不自动进入编码。仅讨论含义或修改错别字、单句表达时，不需要执行完整流程；当 Review 结论改变范围、交互、生命周期、状态、接口或验收规则时，继续使用本 Skill 完成定向修改。业务字段和流程必须来自当前项目，不把“任务插队”的具体规则固化为通用模板。

## 核心设计

### 1. 证据有优先级

发生冲突时，按以下顺序判断：

1. 当前讨论中用户已经确认的结论。
2. 最新需求、接口或协议。
3. 当前代码和运行行为。
4. 旧方案和旧假设。

不能确认且会改变方案的内容，要先提问；不影响主方案的小问题，采用最小假设并写明。

每条强制规则都应能归入 `用户已确认`、`需求或接口已定义`、`代码已验证` 或 `待确认`。没有实际读取代码时，不能写成“当前代码已经如此”；需求没有提到的状态，也不能直接解释为“不支持”。

资料不完整时，输出应明确分成 `已确认`、`建议默认值（待确认）` 和 `待确认`。常见 UX 只能作为建议，不能直接写成正式规则或验收项。

### 2. 复杂功能先判断是否需要架构侦察

以下任一情况成立时，应把功能视为复杂：

- 跨越多个前端、服务、后端或持久化边界。
- 状态归属、身份标识、事实源或实际运行路径不清楚。
- 涉及异步任务、WebSocket、重试、并发、恢复或清理。
- 常规代码追踪不足以可靠确认当前行为。

复杂功能需要先判断当前会话是否可使用 `$feature-architecture-recon`：

1. Skill 可用时，先用它梳理当前流程、事实源、不变量、失败路径和证据链。
2. Skill 不可用时，先询问用户是否引入，不得自动安装、关联或复制。
3. 用户同意时，按用户批准的方式引入并完成侦察，再继续编写 Spec。
4. 用户不同意时，使用 `write-frontend-spec` 内置的最小代码追踪流程继续，并明确证据范围和剩余未知项。

简单功能、全新功能或现状已经验证完整时，可以跳过。用户默认只需调用 `$write-frontend-spec`；架构侦察只提供现状证据，不能替代目标业务决策。

### 3. 复杂功能先经过同文件前置确认

前置确认直接写在目标 Spec 的第 0 章，它用于先确认“要做什么”，正式章节再回答“如何实现”。

满足以下任一条件时，默认需要前置确认：

- 存在容易混淆的业务术语、参考项目概念或相似交互。
- 包含开关、面板、编辑态、只读态、回显态等多种 UI 状态。
- 涉及开始、结束、取消、切换、退出、失败恢复等生命周期决策。
- 同一数据会被各种消费者使用。
- 用户可见行为规则尚未完整定义。

简单、单路径且需求已经明确的功能可以跳过；跳过时应说明原因。

#### 3.1 确认阶段的文档状态

首次生成目标 Spec 时，只写元数据和第 0 章，不展开完整十段式 Spec：

```markdown
# <功能名称> Spec

> 状态：需求确认中，不可作为实施依据

## 0. Spec 前置确认

### 0.1 实施阶段
### 0.2 术语与参考项目差异
### 0.3 入口与交互矩阵
### 0.4 生命周期矩阵
### 0.5 状态归属与消费边界
### 0.6 Skill 建议方案
### 0.7 待确认问题
### 0.8 确认记录
```

前置确认必须使用用户可见语言，优先通过状态表和行为矩阵说明：用户在什么状态执行什么操作，最终看到什么。术语除了定义，还要说明“用户看到什么”和“不代表什么”。

每项结论必须标记来源：

- `用户已确认`
- `需求或接口已定义`
- `当前代码已验证`
- `参考项目行为，仅供参考`
- `Skill 建议，待确认`

来源必须标记到单项决定，不能用一个“用户已确认”的编号覆盖整章中来源不同的默认值、交互、提示文案和技术选择。一个章节包含多种来源时，应拆分决定，或在表格中逐行标记。

Skill 自拟的入口、开关、默认值、提示文案、退出语义、失败恢复或阶段范围只能放在“Skill 建议方案”或“待确认问题”中，不能直接写成正式规则。

确认阶段不展开完整 TypeScript 接口、内部 adapter、异步身份、并发实现、完整验收标准和风险清单；只有当这些技术选择本身会改变用户行为或系统边界时，才作为决策问题进入第 0 章。

根据功能范围选用以下矩阵；不适用的矩阵应说明原因，不为凑齐模板而补造规则：

- 参考项目差异矩阵：参考行为、本项目保留/删除/修改、来源、待确认点。
- 入口与交互矩阵：页面状态、入口或控件、可见/可用条件、用户操作、画面结果、数据是否保留或清空、是否确认、来源。
- 生命周期矩阵：事件、进入前状态、进入动作、期间限制、正常退出、失败/取消回滚、最终保留状态、来源。
- 状态归属矩阵：数据或状态、事实来源、用途、建立时机、释放时机、是否持久化。
- 消费边界矩阵：主视图、总览图、截图、浏览器回显、SSR 等消费者是否读取数据、如何呈现、失败时如何清理、来源。

#### 3.2 集中确认闸门

Codex 应一次性按以下主题汇总阻断问题，避免用户在长篇 Spec 中零散追问：

1. 术语与范围。
2. 入口、控件和交互。
3. 生命周期。
4. 数据保存、历史兼容和失败处理。
5. 各页面和运行时消费者的呈现边界。
6. 实施阶段和验收范围。

前置确认闸门只检查第 0 章，不读取尚未展开的正式章节。只有当适用矩阵已经覆盖、阻断问题清零、Skill 建议仍与正式决定分离，并且用户明确表示“前置确认通过”或同等含义时，才能进入正式 Spec。确认结果记录在 `0.8 确认记录`；未获得明确确认时，不得自行补全剩余行为并继续展开正式章节。

前置确认 Review 只关注产品含义、交互和范围；正式 Spec Review 主要关注技术可行性、规则完整性和章节一致性，避免让使用者在同一轮同时审核两类问题。

#### 3.3 确认后的同文件转换

确认通过后：

1. 把文档状态改为 `需求已澄清，待实现`。
2. 按十段式目录展开正式 Spec。
3. 把第 0 章收缩为“已确认决策索引”，只保留决策编号、简短结论和正式规则链接。
4. 具体逻辑只写在正式规则章节；决策索引不得复制完整流程。

```markdown
## 0. 已确认决策索引

| 编号 | 已确认结论 | 来源 | 正式规则 | 影响章节 |
| ---- | ---------- | ---- | -------- | -------- |
| C1   | <简短结论> | <来源> | [R1](#r1) | <章节> |
```

第 0 章是查找入口，不是第二套事实来源。确认过程中的备选方案由 Git 历史保留，不继续混在正式 Spec 中。

#### 3.4 需求重开与定向复审

正式 Spec 完成后发现新的业务问题时：

1. 将状态改为 `需求重新确认中，不可作为实施依据`。
2. 在第 0 章登记新决策、备选方案和影响章节。
3. 用户确认前暂停修改依赖该决策的正式章节。
4. 用户确认后一次性更新所有受影响章节，再恢复 `需求已澄清，待实现`。

决策索引应记录影响范围，例如：

| 决策 | 影响章节 |
| ---- | -------- |
| 历史回显退出语义 | 生命周期、浏览器回显、无辅助信息呈现、Trade-off、验收标准 |

这样后续修改可以定向检查受影响章节，不必每次重新审核整篇文档。

Review 后的处理分三类：

- 仅解释含义，或修改错别字、单句表达：直接处理，不重开需求，也不执行完整检查。
- 用户已经明确给出新的业务结论：记录决定及影响章节，使用本 Skill 一次性更新相关规则、接口、Trade-off、验收和风险。
- Review 暴露出尚未决定的业务问题：按本节重开需求，确认前暂停修改依赖该决定的正式章节。

检查范围分三层：

1. 前置确认只检查第 0 章、适用矩阵和确认记录。
2. 正式 Spec 首次完成时全文检查一次，确认前置决定已经落入正式章节，且范围、数据、接口、生命周期和验收相互一致。
3. 后续修改默认检查决策索引、影响章节及对应验收和风险；只有变更影响范围、核心状态归属、持久化结构、主生命周期，或预计影响三个及以上核心章节时，才重新检查全文。

### 4. 默认使用十段式目录

```text
目标 / 非目标
现状与问题
架构图与流程图
关键数据结构
上下游依赖
关键假设与约束
接口
Trade-off
验收标准
风险、兼容性
```

这套顺序先固定范围，再说明证据和设计，最后落到验收与风险。章节确实不适用时可以省略，但不能用省略章节来隐藏未澄清的问题。

### 5. 同一规则只完整描述一次

复杂流程、并发规则或状态映射应放在一个主章节中完整定义。其他章节通过锚点引用，不再复制一遍。

- `关键假设与约束`、`接口`负责定义规则。
- `验收标准`负责验证规则，不重新发明规则。
- `现状与问题`只写当前事实，不混入目标设计。

引用处仍应写出当前读者需要知道的一句结论，再链接到完整规则；不能只写“见 R9”迫使读者跳转后才能知道基本结果。验收标准可以重述场景、操作和预期结果，但不重复内部实现机制。

### 6. 同时写清行为和契约

Spec 不能只写接口，也不能只写页面。重要流程需要同时覆盖：

- 用户看到什么、能做什么。
- 前端以哪个字段或快照为准。
- 请求、响应、事件和错误如何解释。
- loading、禁用、空数据、失败、重试和清理如何处理。
- 并发、乱序、幂等或历史兼容由哪一端负责。

先确认用户行为和产品边界，再设计状态、接口和内部实现。入口、关闭语义、正常退出、失败回滚等行为尚未确认时，不提前固化 adapter、内部身份、快照或并发机制。

批量处理、部分失败、刷新时机、选择保留、重试策略和请求形态都属于会改变实现的决策。来源没有定义时，应先列为待确认，不能套用常见做法补齐。

### 7. 内容保持精确、简洁明了

优先使用：

- 表格：现状、映射、依赖、错误码、取舍。
- Mermaid：跨组件协作、多角色参与、分支较多、时序明确或涉及状态流转的流程。
- TypeScript / JSON：需要逐字段确认的契约。
- 明确措辞：`必须`、`只`、`不得`、`失败时保留`。

避免使用“适当处理”“按需刷新”“保持兼容”这类无法直接实现或验收的表达。

## 推荐工作流

```text
读取最新需求和用户确认
↓
判断是否需要架构侦察；复杂且 Skill 不可用时先询问用户
↓
核对当前代码、接口和真实数据来源
↓
判断是否需要前置确认
↓
复杂功能：只生成目标 Spec 的第 0 章，集中确认术语、交互、生命周期、消费边界和实施阶段
↓
阻断问题清零，用户明确确认前置内容
↓
将第 0 章转换为已确认决策索引，按十段式目录展开正式 Spec
↓
首次完成正式 Spec：全文检查单一事实源、交叉引用和契约一致性
↓
校验文档结构并执行 git diff --check

Review 后修改：
仅改文案 → 定点检查
改变已确认规则 → 按决策索引检查影响章节、验收和风险
出现未决业务问题 → 重开前置确认
影响多个核心章节 → 重新全文检查
```

## 完成标准

一份合格的输出应满足：

- 开发者无需重新猜测关键行为。
- 复杂功能在展开正式 Spec 前已获得用户明确确认；确认前的文档明确标记为不可实施。
- 前置确认的适用矩阵已经覆盖，且确认记录可直接查到，不依赖重新阅读全文推断。
- 未经用户确认，Skill 自行建议的交互、参考项目行为和通用 UX 做法，只能列为待确认项，不能作为本项目必须实现和验收的要求。
- 前置确认与正式 Spec 使用同一文件；确认后第 0 章只保留决策索引，不形成第二套事实来源。
- 页面行为和接口语义能一一对应。
- 复杂流程包含成功、失败和边界状态。
- 验收项可以观察或测试，并包含关键反例。
- 未确认的决策不进入正式验收项。
- 每条强制规则都有单项来源，不能用一个确认编号覆盖整章中的混合来源。
- 复杂功能经过架构侦察门槛，不会静默引入其他 Skill。
- 正式 Spec 首次完成时经过一次全文一致性检查；后续修改按影响章节定向复审，跨核心章节变化才重新全文检查。
- 引用处包含必要的结果摘要，验收项写明可观察结果，不要求读者仅凭链接重建场景。
- 文档没有互相冲突的重复定义。
- 没有无依据的字段、迁移、兜底或未来范围。
